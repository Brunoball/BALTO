============================

CAMBIAR ENTORNO = CAMBIAR UNA SOLA LÍNEA EN .env.playwright

PRUEBA / STAGING:
PW_API_URL=https://balto.3devsnet.com/BALTO_SERVICIOS/api/routes

PRODUCCIÓN REAL:
PW_API_URL=https://app.balto.com.ar/BALTO_SERVICIOS/api/routes

No cambies usuario ni contraseña: el testing los elige automáticamente.


REQUISITO DEL BACKEND PARA SUITE MUTABLE
----------------------------------------
El hardening final deja las herramientas E2E APAGADAS por defecto.
En el .env PRIVADO del backend de PRUEBA/STAGING debe existir:
BALTO_E2E_TOOLS_ENABLED=1

En PRODUCCIÓN debe quedar:
BALTO_E2E_TOOLS_ENABLED=0

Si PW_ALLOW_MUTATIONS=1 y el flag E2E del backend está apagado, la suite falla
antes de mutar datos con un mensaje explícito. Esto es intencional: no se corre
una suite mutable sin cleanup seguro.

SUITE PRINCIPAL / FUNCIONAL
--------------------------
La suite interna nueva vive en tests/internal y todos sus títulos llevan @internal.
Para correr SOLAMENTE el testing principal de siempre:

npx playwright test --project=chromium --workers=1 --reporter=list --grep-invert @internal

COBERTURA NUEVA DE SERVICIOS / MOVIMIENTOS
------------------------------------------
- El servicio no tiene stock propio.
- La composición muestra todos los Materiales/Insumos, incluso sin control de stock.
- Composición cerrada por defecto y expandible.
- Edición manual de cantidades/componentes por movimiento.
- Snapshot congelado en la venta.
- Sólo componentes con controla_stock=1 descuentan/reponen inventario.
- Stock insuficiente: bloqueo preventivo frontend + validación backend.
- Cantidad de servicio entera en UI y backend.
- Selector Precio de venta / Precio de costo en Ventas, Presupuestos y Otros ingresos.
- Presupuesto no consume stock; al asignarlo como venta sí.
- Contrato de PDFs/remitos: nombre del servicio + "Incluye" sin precios internos,
  y nombre del servicio incorporado al nombre del archivo.

TESTING INTERNO - BACKEND
-------------------------
La suite secundaria agrega una única acción READ-ONLY dentro del módulo de testing:
config_testing_e2e_integrity.

Está protegida exactamente igual que el cleanup existente:
- requiere sesión ADMIN;
- sólo existe si BALTO_E2E_TOOLS_ENABLED=1;
- en producción debe permanecer apagada;
- no acepta SQL arbitrario ni modifica datos.

Valida stock_actual vs historial, continuidad y aritmética del historial de stock,
stock negativo, matemática subtotal/IVA/total, pagos no positivos, estados y usos
de cheques, y relaciones huérfanas.

LIMPIEZA AUTOMÁTICA
-------------------
- Al iniciar la suite se eliminan residuos PW-* de corridas anteriores.
- Al terminar cada worker se eliminan todos los datos PW-* de esa corrida, incluso si un test falla.
- También se eliminan relaciones, movimientos, modelos de presupuesto, historial y archivos físicos adjuntos creados por Playwright.
- Si la limpieza deja aunque sea un registro o no puede borrar un archivo físico, la corrida falla y lo informa.

Si una corrida se corta por Ctrl+C, cierre de terminal/PC o un crash, podés limpiar manualmente con:
node tests/cleanup-now.mjs

REGRESIÓN RECIBOS / ÓRDENES DE PAGO AGRUPADOS
----------------------------------------------
Valida el fix de cuenta corriente cuando una misma operación se paga con más de un medio:
- Recibo con CHEQUE + otro medio aparece como una sola fila por el total.
- Orden de pago con CHEQUE + otro medio aparece como una sola fila por el total.
- La fila agrupada conserva un único comprobante y expone sus dos aplicaciones internas.
- Al eliminar Recibo/Orden se eliminan juntas todas las aplicaciones y el comprobante.
- No queda un pago parcial fantasma ni una fila sobreviviente sin PDF.
- En Orden de pago, el cheque utilizado vuelve a EN_CARTERA al revertir la operación completa.
- En Recibo, el cheque recibido permanece correctamente en cartera.

Sólo esta regresión:
npx playwright test tests/36-grouped-payment-current-account-regression.spec.js --project=chromium --workers=1 --reporter=list

REGRESIÓN OTROS INGRESOS LIBRE / CLIENTE FISCAL OPCIONAL
--------------------------------------------------------
Valida el ajuste final de Otros Ingresos:
- Guardar un Otro Ingreso NO selecciona cliente automáticamente.
- El movimiento se crea con id_cliente = NULL y cliente_nombre = NULL.
- Incluso si se seleccionó un cliente para el circuito fiscal, al guardar sin facturar
  ese cliente no queda asociado comercialmente al movimiento.
- Facturar sin cliente se bloquea antes de crear el ingreso y muestra la advertencia
  "Seleccioná un cliente antes de facturar".
- Al seleccionar cliente explícitamente, el flujo fiscal existente (ficha fiscal o CUIT)
  sigue funcionando sin alterar la naturaleza libre del movimiento.
- Otros Ingresos continúa sin mover stock.

Sólo esta cobertura:
npx playwright test tests/07-other-movements.spec.js tests/17-other-income-fiscal.spec.js --project=chromium --workers=1 --reporter=list
